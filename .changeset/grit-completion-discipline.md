The developer group gains an eighteenth skill, `grit`, which makes the repository's verification-before-completion doctrine runnable. `VERIFICATION.md` has said since the no-mistake gate landed that a process finishing without error is not evidence of success, but nothing in the pipeline executed a check and recorded what it found; the doctrine was enforced as prose and as tests asserting the prose was still present. `grit` supplies the missing machinery, adapted from Leonxlnx's MIT-licensed `unlazy` and maintained here as first-party code: an acceptance-gate ledger written before implementation, where each gate names one observable outcome, the command that decides it, the output that counts as success, and the evidence recorded when the command runs. Every gate carries one of five dimensions — completeness, accuracy, business value met, efficiency, and thoroughness — each covered by at least one gate or explicitly marked not applicable, the same never-silent-omission discipline the work-item contract already applies to its Governance section. ADR 0006 records why the scripts are adapted and owned here rather than installed as a third-party pack, and why the five dimensions are a taxonomy inside the existing four gates rather than a fifth gate.

A verification depth tree decomposes substantial work into five to ten layers, and the split of authority it needs is written into `orchestrate`'s rubric rather than left implicit. `orchestrate` keeps sole authority over execution shape; `grit` decides only how finely done is split into gates. A gate is a ledger row and a node is an agent, so deepening a ledger adds checks rather than agents and never trips the rubric's overhead rules. Depth selection is human-first: a depth the user states is taken as given, and absent one the orchestrator recommends a depth with the signals that produced it, for a person to accept or override. Below the substantial threshold the rubric returns a flat ledger, because a five-layer tree on a one-file fix is overhead. Verification depth stays separate from the two to four stack layers in `STACKING.md`, which bound what a reviewer holds in their head rather than what a verifier checks.

The discipline is threaded through the pipelines that already existed rather than bolted alongside them. On both engines, `deliver-work-item` authors the ledger during planning, materializes it before the first source change, executes it during verification, and carries the met, unmet, and abandoned audit into the pull request body; `assess-work-item` treats an acceptance criterion that cannot become a gate as a blocking finding; and `shakedown-pr` spot-checks a claimed audit against the diff. The work-item contract's definition of done now requires zero unmet gates, SDLC Gate 3 executes the ledger, and the pm gates' blind-spot review asks the evidence-ledger question, with Framing fixing the verification depth for a substantial initiative.

The repository also ships its first agent hooks, all opt-in. A Claude Code stop hook blocks a session while unmet gates remain, counting a progress hash so metadata-only edits do not reset it and releasing after six blocks without progress so a stuck session is never trapped. OpenCode gets a `grit-verify` command and a verify-agent rule making unmet gates preclude a handoff-ready verdict. GitHub Copilot has no hook runtime, so it is covered by an instructions-file rule and by `grit-gates.yml`, a dispatch-only Action that lints the ledger and runs the checker in its parse-only mode — no secret and no approval store required, and the backstop that covers every tool without a hook of its own. A human reads and approves each check command once before it can execute, bound to the exact command, directory, shell, and environment, with approvals stored outside the repository so a repository write cannot grant itself the right to run.
