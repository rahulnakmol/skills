# The RAID registers

Four registers, one discipline: nothing that could derail the initiative lives only in someone's memory or a chat thread. Every entry carries an owner, because a risk with no owner is a risk nobody actually manages.

## Risks

Something that might happen and would hurt the initiative if it did. Each risk carries a likelihood, an impact, a named owner, and a mitigation — the action being taken now to reduce likelihood or impact, not a hope that it resolves itself. A risk register with no mitigation column is just a list of worries.

## Assumptions

Something taken as true without current proof, load-bearing enough that the plan changes if it turns out false. Every assumption names the owner responsible for validating it and the point at which it will be checked — an assumption nobody is tracking quietly becomes an unexamined belief.

## Issues

Something that has already happened and needs resolving now — the past-tense counterpart to a risk. Every issue carries an owner and a path to resolution; an issue sitting in the register with no owner and no movement across several reporting cycles is the clearest sign a status update is being generated rather than acted on.

## Dependencies

Something this initiative needs from outside its own control — another team, another system, another initiative's delivery. The dependency board `roadmap` reads directly from this register rather than keeping a second copy, so a slipped dependency shows up in the sequencing the moment it slips, not a reporting cycle later.

## The status narrative

The two-minute sponsor status narrative is generated directly from the four registers, never hand-assembled twice — the register is the source of truth, and the narrative is one view onto it. If the narrative and the register ever disagree, the register is right and the narrative was stale.
