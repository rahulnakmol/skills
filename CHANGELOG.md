## 0.6.0

### Minor Changes

- 1deb8bd: Two new skills address work that outgrows a single agent session. The pm group gains a seventeenth skill, `chart`: an initiative too large or too uncertain for `discover` → `map` → `carve` to run in one pass is charted as decision tickets on the team's tracker, each ticket asking one question sized to one session and carrying one of four types — evidence, option, alignment, or enablement — that decides who resolves it and whether it can run in parallel. The chart is an index rather than a store, so a decision lives in exactly one place; four ticket states (ready, blocked, claimed, closed) make the takeable edge of the plan readable without opening anything; a claim protocol lets several agent sessions work one chart concurrently; and what cannot be settled leaves as a `raid` entry rather than sitting open forever. `report` now sources Progress and Priorities from a chart where one exists, so a large effort produces status without anyone writing a status update, and `ask-pm` routes "this is too big to plan in one go" to it.

  The productivity group ships its first skill, `brief`: the rules, definitions, and boundaries a team's agents read, broken into three layers — always-loaded rules, a shared glossary, and on-demand references — and placed in the file each surface actually loads. `SURFACES.md` maps Claude Code, Claude Desktop, Cowork, OpenCode, Codex, Cursor, and Copilot to their rule files, names one canonical file with pointers elsewhere, and covers the two surfaces that have no repository file at all. `RULES.md` covers the anatomy of a rule that fires, why a prohibition underperforms the positive instruction beside it, when the environment should stay the source of truth, and why a rule is tested by running work rather than by rereading the file.

- 1deb8bd: The developer group gains an eighteenth skill, `grit`, which makes the repository's verification-before-completion doctrine runnable. `VERIFICATION.md` has said since the no-mistake gate landed that a process finishing without error is not evidence of success, but nothing in the pipeline executed a check and recorded what it found; the doctrine was enforced as prose and as tests asserting the prose was still present. `grit` supplies the missing machinery, adapted from Leonxlnx's MIT-licensed `unlazy` and maintained here as first-party code: an acceptance-gate ledger written before implementation, where each gate names one observable outcome, the command that decides it, the output that counts as success, and the evidence recorded when the command runs. Every gate carries one of five dimensions — completeness, accuracy, business value met, efficiency, and thoroughness — each covered by at least one gate or explicitly marked not applicable, the same never-silent-omission discipline the work-item contract already applies to its Governance section. ADR 0006 records why the scripts are adapted and owned here rather than installed as a third-party pack, and why the five dimensions are a taxonomy inside the existing four gates rather than a fifth gate.

  A verification depth tree decomposes substantial work into five to ten layers, and the split of authority it needs is written into `orchestrate`'s rubric rather than left implicit. `orchestrate` keeps sole authority over execution shape; `grit` decides only how finely done is split into gates. A gate is a ledger row and a node is an agent, so deepening a ledger adds checks rather than agents and never trips the rubric's overhead rules. Depth selection is human-first: a depth the user states is taken as given, and absent one the orchestrator recommends a depth with the signals that produced it, for a person to accept or override. Below the substantial threshold the rubric returns a flat ledger, because a five-layer tree on a one-file fix is overhead. Verification depth stays separate from the two to four stack layers in `STACKING.md`, which bound what a reviewer holds in their head rather than what a verifier checks.

  The discipline is threaded through the pipelines that already existed rather than bolted alongside them. On both engines, `deliver-work-item` authors the ledger during planning, materializes it before the first source change, executes it during verification, and carries the met, unmet, and abandoned audit into the pull request body; `assess-work-item` treats an acceptance criterion that cannot become a gate as a blocking finding; and `shakedown-pr` spot-checks a claimed audit against the diff. The work-item contract's definition of done now requires zero unmet gates, SDLC Gate 3 executes the ledger, and the pm gates' blind-spot review asks the evidence-ledger question, with Framing fixing the verification depth for a substantial initiative.

  The repository also ships its first agent hooks, all opt-in. A Claude Code stop hook blocks a session while unmet gates remain, counting a progress hash so metadata-only edits do not reset it and releasing after six blocks without progress so a stuck session is never trapped. OpenCode gets a `grit-verify` command and a verify-agent rule making unmet gates preclude a handoff-ready verdict. GitHub Copilot has no hook runtime, so it is covered by an instructions-file rule and by `grit-gates.yml`, a dispatch-only Action that lints the ledger and runs the checker in its parse-only mode — no secret and no approval store required, and the backstop that covers every tool without a hook of its own. A human reads and approves each check command once before it can execute, bound to the exact command, directory, shell, and environment, with approvals stored outside the repository so a repository write cannot grant itself the right to run.

- 1deb8bd: Each skill group now installs on its own, and no group depends on another. The repository has addressed engineers and product managers as separate audiences since it was written, with separate README sections, separate persona ladders, and separate routers, but the packaging never matched that intent: one plugin sourced from the root, one manifest listing every skill, and a link script with no way to select a subset. Installing anything installed everything. Because nothing prevented it, the pm group had accumulated twelve references into developer-group files, so a product manager who wanted only the pm group would have received gate doctrine, a grill protocol, and a report verification that all pointed at files not present. ADR 0007 records the decision and its costs.

  Shared doctrine moves into a sixth group, `core`, which belongs to no audience and which every group may reference on equal terms. It holds `grit`, whose ledger both pipelines call, together with the four documents already read from outside their owning skill: `VERIFICATION.md`, `COVERAGE.md`, `GRILL.md`, and `VALUE.md`. The dependency rule is directional and checkable — any group may reference `core`, no group may reference another group, and `core` references none. Moving `grit` alone would have inverted the violation rather than fixing it, since its method document cited a routing rubric, a stacking convention, and a loop contract that the developer group owns; those references now describe the conventions instead of pointing at another group's files.

  Two defects surfaced that a document-shaped test could not see. Both the developer and pm groups owned a skill directory named `orchestrate`, and the link script names each symlink after the directory basename, so a full install produced thirty-six symlinks for thirty-seven skills and the developer group's orchestration skill — cited by `sdlc`, the work-item contract, and `grit` — was silently overwritten and unreachable. Both skills are renamed rather than one, because the shared name was carrying two different jobs: the developer skill becomes `conduct`, which selects execution shape and assigns a model per node, and the pm skill becomes `arrange`, which chooses the shape of an inquiry before a round begins. Separately, no group-level doctrine had ever been installed at all: `GATES.md`, `AGENT-OWNERSHIP.md`, `DDDD.md` and their siblings sit at a group's top level rather than inside a skill directory, so nothing linked them and every skill instructing a reader to run a checklist named a file absent from the install.

  Installation is now scoped. `link-skills.sh` takes `--group` and `--skill`, both repeatable, plus `--target`, `--list`, `--dry-run`, and `--no-core`, and a bare target directory still works. Selecting a group also links `core`, since no group resolves without it, and each selected group carries a doctrine link so its top-level documents are present. A pm-only install now resolves completely: seventeen pm skills, `grit`, both doctrine sets, every referenced document, and no developer skills.

  Four tests in `test/structure/group-independence.test.mjs` reason about an installed set rather than a document, which is the class of check that would have caught the collision: basenames are unique repository-wide, linking the pack yields one entry per promoted skill with every link resolving, no group references another while `core` references none, and the pre-move doctrine paths are gone so a stale reference fails loudly. Each was verified to fail under a planted violation before being trusted.

  The promoted set shrinks from thirty-seven skills to thirty-four, on the reasoning that a skill a model cannot reliably select is worth nothing however good its doctrine. `assure` and `maintain` fold into `operate`, which now runs three named lanes — reliability, quality, and maintenance — routes to all three adapter targets the originals carried, and describes itself in the verbs and artifacts someone actually types rather than as a category. `prd-validate` folds into `prd-draft` as a sibling validation document run as a step, which also closes the gap the split created, where a PRD could be drafted and handed onward without the check ever running. Nothing was dropped: `maintain`'s cadence document moved rather than being deleted.

  `press` becomes a working skill rather than a promise. It offered to render a requirements document to a branded PDF while shipping a palette file and no renderer, with a procedure that said to run the script "when present" under a directory that did not exist. It now carries a zero-dependency renderer that reads every color, font, and page measurement from `PALETTE.md`, escapes document text so markup inside a document renders as text rather than as live tags, and allowlists link schemes so an unsafe target keeps its words and loses its anchor. It refuses to claim an artifact it did not produce: with no headless browser it writes the HTML, prints why the PDF step could not run, creates no file named `.pdf`, and exits non-zero because the requested artifact does not exist; when a browser exits cleanly it still opens the file and confirms it is a PDF before reporting one. Press also renders any approved markdown document rather than specifically a requirements document from another group, which removes the branding group's dependency on the developer group and puts the sign-off where it belongs, with the document's owner.

  Anyone who has already installed the pack should know that `orchestrate`, `assure`, `maintain`, and `prd-validate` are no longer present under those names. `conduct` and `arrange` replace the first; `operate` and `prd-draft` absorb the rest.

- 1deb8bd: The repository gains a way to measure whether its skills can be selected at all. The deterministic harness proves the tree is well formed — manifests agree, doctrine documents carry their headings, scripts honor their contracts — but a skill is a prompt that has to win selection against every sibling, and a file can be perfectly well formed and never chosen. Nothing here could previously detect one.

  `test/eval/run-routing.mjs` reads every promoted skill's description from the tree, presents the catalog to a model alongside a labeled request, and records which skill comes back. Scoring is exact-match on the name, so no judge model is involved. Each case runs several times, because selection is stochastic and a case that routes correctly once and wrongly twice is not a passing case; the default threshold is every run, since a skill selected two times in three fails a third of the people who ask for it. Runs write a dated scorecard to `test/eval/results`, so a regression is a diff between two files rather than something someone has to remember, and a missing model is recorded as a skip rather than scored as a pass.

  The eval earned its place before it was committed. `conduct` and `arrange`, both renamed from `orchestrate`, had been left with descriptions nearly identical in shape, and a request using `conduct`'s own vocabulary routed to `arrange` on two runs out of three while every structural test stayed green. It was also used to test the claim that a thin description costs selection: `operate`'s four-word predecessor still won uncontested requests and dropped to one run in two on the contested one, which places the cost more precisely than the claim did — a thin description loses on contested ground, where selection is actually decided.

  Routing accuracy is necessary and not sufficient, and the README says so plainly: it establishes that the right skill was chosen, not that invoking it produced better work than not invoking it. That paired-arm question needs planted defects, per-case checklists, and a judge from a different model family than the one being graded, and is not built yet.

  Because every case is a model call, the eval runs weekly or on demand rather than per pull request, and a test fails if a `pull_request` trigger is ever added so the cost cannot start quietly. What does run on every pull request is everything needing no model: the table is valid, names skills that exist, covers the catalog, and the runner states its contract.
